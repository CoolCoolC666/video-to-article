## 一、结论摘要

三个诉求都能做，但**有一个必须先纠正的认知**，否则整个设计会建在流沙上：

> **`llm.provider` 不是「厂商名」，而是「协议开关」。**

你截图里填的 `provider=openai` + `base_url=https://api.minimaxi.com/v1`，
真实含义是「**用 OpenAI 兼容协议**去连 **MiniMax 这个厂商**」。
`providers/llm.py:44-47` 里 provider 只有两个分支：`openai` / `anthropic`，
它决定的是**用哪个 SDK、发什么格式的请求**，跟厂商无关。

所以「Provider 实际需要填格式」这个诉求的真正解法不是加更多选项，
而是**把「协议」和「厂商」拆成两个正交字段**。详见 §3.2。

三个诉求的可行性与实测结论：

| 诉求 | 可行性 | 关键约束 |
| --- | --- | --- |
| 自动抓取模型列表 | ✅ 可行 | **SDK 路径当前不可用**（缺依赖），须用 `requests` 直连（已实测通过） |
| Provider 格式 | ✅ 可行 | 需拆分 protocol / vendor 两个概念 |
| 多档案保存/删除/管理 | ✅ 可行 | 存储结构有坑，见 §3.3 的 `deep_update` 分析 |

**建议实施顺序**：§5 的阶段 1 → 2 → 3，每阶段可独立验证、可独立回滚。

## 二、现状勘察

### 2.1 配置是「单条扁平结构」

`config.json`：

```json
"llm": {
  "provider": "openai",
  "api_key": "sk-***",
  "base_url": "https://api.minimaxi.com/v1",
  "model": "MiniMax-M3",
  "temperature": 0.3,
  "max_tokens": 520000,
  "timeout_seconds": 180,
  "max_retries": 3
}
```

8 个字段**只能存一套**。UI 是 8 个裸控件（`settings_dialog.py:145-152`），
`_collect_updates():1040-1048` 全量重写这个块。切厂商 = 手工重打 4 个字段
（Provider / API Key / Base URL / Model），其中 Model 名最难手打。

### 2.2 `provider` 字段被「过度简化」

```python
# providers/llm.py:43-50
if provider == "openai":
    return _optimize_with_openai(...)      # 走 openai SDK + base_url
if provider == "anthropic":
    return _optimize_with_anthropic(...)   # 走 anthropic SDK，**base_url 被忽略**
logger.error(f"不支持的提供商: {provider}")
```

两个分支的能力差异很大：

| | openai 分支 | anthropic 分支 |
| --- | --- | --- |
| SDK | `openai` | `anthropic` |
| base_url | 生效 | **完全忽略**（`llm.py:133` 只传了 `api_key`） |
| 鉴权头 | `Authorization: Bearer` | `x-api-key` |
| 换厂商 | 改 base_url 即可 | 改不了（Anthropic SDK 不吃 base_url） |

也就是说，**「支持多少厂商」这件事，目前等于「支持多少个 OpenAI 兼容的中转/云」**。
真正非兼容的（Anthropic 原生）只能二选一，且不能指向自建代理。

### 2.3 厂商判断已经在别处「打补丁」了

`cover.py`（图像生成）那边已经踩过同样的坑，现状是**靠 base_url 猜**：

```python
def is_xai_image_api(base_url: str) -> bool:
    return "api.x.ai" in str(base_url or "").lower()      # cover.py:563

def normalize_openai_edit_strategies(cover_config, base_url) -> list[str]:
    if "api.openai.com" in str(base_url): return ["multipart", "json_image_url"]
    if is_xai_image_api(base_url):         return ["json_image_url", "multipart"]
    return ["json_image_url", "multipart"]
```

**这是重要的先例证据**：厂商相关的判断已经存在，但以「字符串嗅探 base_url」的形式
散落在各处。新设计如果不在 LLM 侧收口，迟早会把这套脏活复制一份过来。

## 三、逐个诉求的设计

### 3.1 自动抓取模型列表

#### 3.1.1 实测结论一：SDK 路径**当前不可用**

```
openai 版本：3.8.0
c.chat     → 可用（懒加载，当前 LLM 调用不受影响）
c.models   → ModuleNotFoundError: No module named 'jiter'
```

`pyproject.toml` 只声明了 `openai>=1.0.0`，**没有锁 `jiter`**。
而 `openai` 从 2.x 起把 `jiter` 变成了硬依赖 —— 声明 `>=1.0.0` 装出来的
可能是 3.x，但项目没跟着声明它的传递依赖。

> ⚠ 这意味着**任何走 `client.models.list()` 的实现，在当前依赖下会直接崩**。
> 这是实测结论，不是推测。

#### 3.1.2 实测结论二：`requests` 直连**可用**（用你的真实 base_url，只读不计费）

```
GET https://api.minimaxi.com/v1/models
  → HTTP 200
  → {"object": "list", "data": [{"id", "object", "created", "owned_by"}]}

返回 8 个模型：
  MiniMax-M3            MiniMax-M2.7        MiniMax-M2.7-highspeed
  MiniMax-M2.5          MiniMax-M2.5-highspeed
  MiniMax-M2.1          MiniMax-M2.1-highspeed
  MiniMax-M2

当前 config 配的 MiniMax-M3 ∈ 该列表 ✓
```

标准 OpenAI 格式。

#### 3.1.3 建议实现

```python
# 建议新增：providers/llm_models.py
def fetch_models(base_url: str, api_key: str, timeout: int = 15) -> list[str]:
    """GET {base_url}/models → 模型 id 列表。失败返回 []。

    ⚠ 必须用 requests 直连，不要用 openai SDK 的 client.models.list()：
    openai>=2.x 的 models 资源依赖 jiter，而本项目 pyproject 没声明它
    （实测 ModuleNotFoundError）。直连还能绕开 SDK 对响应格式的额外校验，
    对国产 provider 兼容性更好。
    """
```

**降级链**（因为不是所有 provider 都实现 `/models`）：

```
1. requests GET {base_url}/models              ← 主路径，已实测
2. 失败 → 读 profile 里上次抓到的缓存（见 3.3 的 models_cache 字段）
3. 失败 → 提示「该服务未提供模型列表，请手动填写」，Model 字段保持可编辑
4. 任何情况都不阻塞：抓模型失败 ≠ 配置不能保存
```

**必须处理的兼容性坑**（各家 `/models` 差异很大）：

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 端点不存在 | 404 / HTML 页面 | 识别 `Content-Type` 非 JSON 直接判失败，走降级 |
| 无鉴权也能列 | 返回全部但不含你有权用的 | 不做过滤，但 UI 要提示「以服务端返回为准」 |
| 混入非对话模型 | 返回 embedding / tts / rerank | 可选正则过滤（如 `embedding\|tts\|whisper`），**默认不滤** |
| 分页 | 只返回前 N 条 | 尝试 `?limit=200`；拿不到就在 UI 标注「可能不完整」 |
| 慢 | 首包 > 10s | 后台线程 + 超时，**不阻塞 UI**（见 4.2） |

> 过滤策略建议**默认不过滤**。宁可多列几个让用户自己选，
> 也不要「智能过滤」把用户唯一的可用模型藏起来。

### 3.2 Provider 格式：拆成 protocol / vendor

#### 3.2.1 概念划分

| 概念 | 含义 | 取值 | 决定什么 |
| --- | --- | --- | --- |
| **protocol**（协议） | 请求/响应的线格式 | `openai_chat` / `anthropic` / `custom_post` | 用哪个 SDK、什么鉴权头、什么 body |
| **vendor**（厂商） | 服务提供方 | `openai` / `minimax` / `deepseek` / `qwen` / `custom` | 只用于：预填 Base URL、日志标识、UI 归类、模型名前缀提示 |

**关键**：绝大多数厂商是 `protocol=openai_chat`，只是 `vendor` 和 `base_url` 不同。
把它们塞进一个 `provider` 字段，就是现在痛点的根源。

#### 3.2.2 迁移映射（向后兼容）

现有配置**必须继续能用**，不能要求用户手动改：

| 旧 `provider` | 新 protocol | 新 vendor |
| --- | --- | --- |
| `openai` | `openai_chat` | 从 base_url 猜（`api.openai.com`→openai，否则 custom） |
| `anthropic` | `anthropic` | anthropic |
| （空 / 其他） | `openai_chat` | custom |

判定逻辑放在一处，比如 `providers/llm_protocol.py`：

```python
def resolve_protocol(llm_cfg: dict) -> str:
    p = (llm_cfg.get("protocol") or "").strip()
    if p:
        return p
    legacy = (llm_cfg.get("provider") or "openai").strip().lower()
    return "anthropic" if legacy == "anthropic" else "openai_chat"
```

`optimize_text_with_llm()` 改用 `resolve_protocol()`，**旧配置零改动继续跑**。

#### 3.2.3 顺带解决 vendor 嗅探的脏活

`cover.py:563` 的 `is_xai_image_api(base_url)` 可以改成查 profile 里的 `vendor`：

```python
# 改前：靠字符串嗅探
return "api.x.ai" in base_url.lower()
# 改后：读显式配置，猜不中再回落嗅探
return (profile.get("vendor") == "xai") or (guess_vendor_from_url(base_url) == "xai")
```

**注意**：这一步**不在本轮范围内**。图像侧的改造建议单独立项，
不要和大模型 Tab 混在一个 commit 里 —— 两者的回归测试完全不同。

### 3.3 多档案的保存 / 删除 / 管理

#### 3.3.1 存储结构

**推荐：放在 `config.json` 的 `llm` 块里，用「列表」而不是「字典」。**

```jsonc
"llm": {
  // ↓ 保留现有 8 个字段不动（继续是"当前生效配置"，零迁移成本）
  "provider": "openai",
  "api_key": "sk-***",
  "base_url": "https://api.minimaxi.com/v1",
  "model": "MiniMax-M3",
  "temperature": 0.3,
  "max_tokens": 520000,
  "timeout_seconds": 180,
  "max_retries": 3,

  // ↓ 新增：多档案
  "active_profile": "minimax-m3",       // 当前生效的档案 id
  "profiles": [
    {
      "id": "minimax-m3",                // 稳定标识（改名不影响引用）
      "label": "MiniMax M3（主力）",      // 给人看的名字
      "protocol": "openai_chat",
      "vendor": "minimax",
      "base_url": "https://api.minimaxi.com/v1",
      "api_key": "sk-***",
      "model": "MiniMax-M3",
      "temperature": 0.3,
      "max_tokens": 520000,
      "timeout_seconds": 180,
      "max_retries": 3,
      "models_cache": ["MiniMax-M3", "..."],   // 上次抓到的模型列表（离线兜底）
      "models_fetched_at": 1780272000          // 抓取时间戳，用于 UI 显示"3 天前抓的"
    },
    { "id": "deepseek-v3", "label": "DeepSeek V3（备用）", "...": "..." }
  ]
}
```

#### 3.3.2 ⚠ 关键坑：`deep_update` 对 list 和 dict 的行为**完全不同**

`config.py` 的 `deep_update` 是递归合并：

```python
for key, value in updates.items():
    if isinstance(value, dict) and isinstance(base.get(key), dict):
        deep_update(base[key], value)   # dict → 递归合并
    else:
        base[key] = value               # 其他（含 list）→ 整体替换
```

推论（**这决定了档案必须用 list**）：

| profiles 存成 | 删除一个档案时 | 风险 |
| --- | --- | --- |
| **list** | 必须整体重写列表 | ✅ 干净，删除即替换 |
| dict（key=档案 id） | `deep_update` 会**递归合并**，删掉的 key **不会消失** | ❌ 幽灵档案，删不掉 |

> **所以：档案必须用 list，且删除操作必须显式写出「删后剩余的完整列表」。**
> 这是本设计里最容易埋雷、也最难在 review 时一眼看出的一处，已写进代码注释与测试。

另外，`_collect_updates()` **不需要**返回 `profiles` —— 只要它不出现在 updates 里，
`deep_update` 就不会碰它，档案天然存活。这降低了改动面。

#### 3.3.3 密钥安全

| 事项 | 现状 / 建议 |
| --- | --- |
| 存放位置 | `config.json`，已在 `.gitignore`（`config.json` / `config - *.json`）✅ |
| 日志 | ⚠ **绝不能把 api_key 写进日志**。参照本项目 `custom_post_asr.py` 的做法：**只打印键名不打印值** |
| 导出/截图 | 保存时对 `api_key` 做掩码展示（`sk-c***Wo`），避免用户截图泄露 |
| `config.example.json` | 同步加上 `profiles: []` 占位 + 字段注释 |
| 加密存储 | 本轮**不做**。引入 DPAPI / keyring 会让绿色包分发变复杂，收益不匹配。若以后要做，单独评估 |

#### 3.3.4 `active_profile` 与现有 8 字段的关系

两种方案：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | 保留现有 8 字段作为「当前生效值」，`profiles` 只是模板库。切换档案 = 把档案内容**拷贝**进 8 字段 | 下游 `providers/llm.py` **一行不用改**，零回归风险 | 8 字段与档案可能不同步（需定义"谁是权威"） |
| B | 下游改成直接读 `active_profile` 对应的档案 | 只有一份真相 | 要改 `llm.py` 读配置逻辑，回归面变大 |

**推荐 A**。理由：本轮改动的核心价值是「录入与管理方便」，
不是重构调用链。A 能把风险压到只在设置对话框内，改完跑一遍 smoke 就完事。

同步规则（写在文档 + 代码注释里）：
- 改档案 → 8 字段不动（档案只是模板）
- 切换档案 / 点「应用到当前」 → 档案内容覆盖 8 字段
- 直接改 8 字段 → **不动档案**（避免用户以为是"改档案"）

│  Model           [MiniMax-M3            ▾]  ⟳ 抓取模型  │
│                  （可编辑的 combo：下拉选 + 允许手填）      │

### 4.2 交互要点

| 交互 | 行为 | 关键约束 |
| --- | --- | --- |
| **⟳ 抓取模型** | 后台线程 `GET {base_url}/models` | **不阻塞 UI**；按钮转圈 + 禁用防重复点 |
| 抓取成功 | 填入 Model 下拉 + 记 `models_cache` + 时间戳 | 保留当前已填的值（避免清掉手填的冷门模型） |
| 抓取失败 | Warning 弹窗说明原因 + 保留手填能力 | ⚠ **绝不清空 Model 字段**，绝不让失败阻断保存 |
| **Model 控件** | **可编辑 combo box** | 有些 provider 不给 `/models`，必须留手填口子 |
| 厂商切换 | 自动预填该厂商的常见 Base URL（可改） | 只是预填，不强制 |
| 首次输入 Base URL + Key | 自动触发一次抓取 | 仅当 Model 为空时才自动，避免覆盖用户填好的 |

### 4.3 右下角「管理」入口（用户明确要求的位置）

`settings_dialog.py:73-76` 现在是：

```python
buttons = QDialogButtonBox(QDialogButtonBox.Save | QDialogButtonBox.Cancel)
buttons.accepted.connect(self._save)
buttons.rejected.connect(self.reject)
root.addWidget(buttons)
```

**方案**：在按钮行**左侧**加一个「管理配置档案…」按钮，与 Save/Cancel 同一行。
放左侧而不是挤在 Save/Cancel 中间，是为了不破坏「Save 在最右」的肌肉记忆。

```python
manage_btn = QPushButton("管理配置档案…")
manage_btn.clicked.connect(self._open_profile_manager)
buttons.layout().insertWidget(0, manage_btn)   # 挤在 Cancel 左边，保持 Save 最右
```

`管理…` 弹出一个独立 Dialog：

| 功能 | 说明 |
| --- | --- |
| 列表 | 每行：启用单选 + 名称 + 厂商 + 模型 + 最后使用时间 |
| 新建 | 复制当前 8 字段为新档案（最省事的入口） |
| 重命名 | 只改 `label`，`id` 不动（id 是引用锚点） |
| 删除 | ⚠ 删前二次确认；**不允许删最后一个**（否则 8 字段失去来源） |
| 应用 | 把档案覆盖进 8 字段 |
| 复制 | 复制档案（存两个 Key 很常见：主力 + 备用） |

**不做的事**（明确划界，避免范围蔓延）：
- ❌ 不做档案导入/导出（用户没提，且涉及密钥外流风险）
- ❌ 不做密钥加密存储
- ❌ 不做多档案并行调用 / 自动降级切换（那是另一个需求）

## 五、实施路径（分阶段）

每阶段独立可验证、可回滚。**不要攒成一个 commit。**

### 阶段 1：模型自动抓取（价值最高、风险最低）

| 项 | 内容 |
| --- | --- |
| 改动 | 新增 `providers/llm_models.py::fetch_models()`；Model 换成可编辑 combo + ⟳ 按钮 |
| 依赖 | ⚠ **必须同时处理 `jiter`**：要么 `pyproject` 加 `jiter`，要么坚持 requests 直连（推荐后者，零新依赖） |
| 测试 | `smoke_llm_models.py`：URL 拼接、JSON 解析、404/非 JSON/超时/空列表四种降级、**断言失败时不清空 Model**、**断言不阻塞** |
| 完成判据 | 填入你的 base_url + key → 点 ⟳ → 下拉出现 8 个 MiniMax 模型 |
| 风险 | 低。失败最坏结果是"下拉没内容，手填照旧能用" |

### 阶段 2：多档案存储 + 管理入口

| 项 | 内容 |
| --- | --- |
| 改动 | `_collect_updates` 增读 profiles；新增 `_open_profile_manager`；底部加「管理…」按钮；`config.example.json` 同步 |
| 存储 | `llm.profiles`（**list**）+ `llm.active_profile`，旧 8 字段不动 |

## 八、⚠ 关键前提：fork 的真实用户数是 0

第 4 项决策时你提出「主要是我们的 Fork 分支目前的用户数量不太清楚」。
这条查证了（2026-10-04，GitHub REST API 公开数据）：

### 8.1 实测数据

| 指标 | **你的 fork**<br>`CoolCoolC666/video-to-article` | 上游<br>`DEKVIW/video-to-article` |
| --- | --- | --- |
| stars | **0** | 10 |
| forks | **0** | 2 |
| watchers / subscribers | **0** / **0** | 10 / 0 |
| open issues | 0 | 1 |
| `network_count` | — | **2**（= 仓库本身 + 1 个 fork = **只有你**） |
| 创建时间 | 2026-09-07 | 2026-07-17 |
| 最后 push | 2026-10-03（你） | **2026-07-17**（上游 2 个多月没动） |

**结论：fork 的外部用户数 = 0，唯一使用者是你自己。**

### 8.2 这对设计权衡意味着什么

§5 阶段 3 原本写「必须验证旧 config 零改动仍能跑」，理由是「不能要求用户手动改」。
现在看，这个理由需要**降级**：

| 原考虑 | 实际情况 | 调整后 |
| --- | --- | --- |
| 为「一堆陌生人的奇怪配置」写防御性兼容代码 | 不存在陌生人 | **可以砍掉**。不必处理「provider 写错 / 大小写奇怪 / base_url 带尾斜杠 / 第三方魔改」等长尾 |
| 严格保证老配置零迁移 | 只需保证**你自己**那份 config 不被改坏 | **保留，但成本可大幅降低**：写一次性迁移即可，不需要长期兼容分支 |
| 引入 config 结构的破坏性变更 | 会影响的唯一用户 = 你 | **可以做**，但迁移必须**不碰 api_key**（丢 Key = 你要重新配） |

### 8.3 由此得到的三条实施原则

1. **不为假想的第三方写代码**
   迁移映射表（§3.2.2）只保留「你自己会产生的形态」：
   `provider: "openai"` + minimax base_url 这一条真实路径。
   不必穷举各种畸形的 provider 值。

2. **破坏性变更可以做，但要写一次性迁移**
   建议在 `settings_dialog.load_from_disk()` 里加 `_migrate_llm_config()`：
   检测到旧结构（无 `protocol`）就地补齐并**原样保留 api_key**，
   迁移过一次就打标记，之后不重复执行。

3. **唯一的「老用户」是你自己 → 验收标准是「你自己那份 config 升级后能跑」**
   动手前先 `cp config.json config.json.bak-20261004`，
   升级后用**真实转写**跑一次（不是只跑 smoke），
   确认 API 没被迁移搞坏、Key 还在。

### 8.4 但有一条兼容性**不能省**

`providers/llm.py` 的 `provider` 分支**不能直接删**。
原因不是为第三方，而是为**你自己磁盘上那份 config** —— 如果你半夜把 config 换回旧结构
（绿色包覆盖、git 切回旧 commit），代码要能兜住。
这只是一行 `resolve_protocol()` 的 fallback，成本近乎零，值得留。
