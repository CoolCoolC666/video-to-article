## 二、为什么现有批量不是瓶颈（复用边界）

| 已有能力 | 实现位置 | MCP 是否复用 |
|---|---|---|
| 目录递归 / 清单文件 | `batch.find_local_videos` / `read_batch_file` | ✅ 直接调 |
| 断点续传 | `processor.plan_batch_urls(skip_existing=)` | ✅ 直接调 |
| 批量执行 + 补救轮次 | `processor.process_batch(auto_repair=)` | ✅ 直接调 |
| 报告复查 + 补救脚本 | `processor.check_batch_report` | ✅ 直接调 |
| 只重整不重转 | `processor.process_raw_file` | ✅ 直接调 |
| 输出路径真源 | `output_manager.build_output_paths` | ✅ 直接调 |
| JSON 批量报告 | `process_batch` 末尾 `json.dump` | ✅ **直接当返回体** |

**铁律：MCP 内部 import 上述函数，绝不 subprocess 调 `transcribe.py`。**
否则要写一层正则去解析项目自己 print 的格式，而这层会随项目改动一起烂；
批量规则会变成两份逻辑，改一处漏一处。

MCP 只补三件现有没有的：**异步台账**、**结构化返回**、**配置选择**。

## 三、配置选择（拍板项 6 的设计）

### 三层结构，从粗到细

```
① 配置文件（config_file）    一整套环境，可多份并存
       ↓
② 档案（profile）           单个服务的切换（**项目已有这套机制**）
       ↓
③ 调用参数（overrides）      只影响本次调用
```

优先级：`overrides` > 临时激活的 profile > 配置文件的默认值

### 目录约定

```
configs/                          ← 新增，可选
├── default.json                  ← 等价于当前 config.json
├── course-deepseek.json          ← 只用 DeepSeek，不碰 MiniMax
└── course-r2-dashscope.json      ← 云端 ASR + R2 图床 + DashScope
```

配置文件里可以直接写死要激活的档案：

```jsonc
{
  "llm": { "profiles": [...], "active_profile": "llm3_xxx" },
  "transcribe": { "custom_post": { "profiles": [...], ... } },
  "_active": {                      // ← 新增：这个配置文件默认激活谁
    "llm": "llm3_xxx",
    "asr": "cp3_yyy"
  }
}
```

### 工具参数

```jsonc
{
  "source": "E:/.../1-课件",
  "config": {
    "config_file": "configs/course-deepseek.json",   // 省略 = 用当前 config.json
    "profiles": {                                    // 省略 = 用配置文件里的默认激活
      "llm": "Deepseek（调）",
      "asr": "cp3_1791122303"
    },
    "overrides": { "asr_engine": "custom_post" }      // 只影响本次
  }
}
```

### ⚠ 关键约束：**调用不得污染磁盘上的 active_profile**

Agent 帮你跑一次任务，不该把你的 GUI 当前选择弄乱。
实现上：解析出的配置放进**内存副本**，`config["active_profile"]` 只在副本里改，
**绝不回写 config.json**。若用户确实想永久切换，走 GUI 或显式 `config_apply` 工具。

### 配置类工具

| 工具 | 作用 | 写盘 |
|---|---|---|
| `config_list` | 列出可用配置文件 + 每份里的档案清单（**档案名脱敏**） | ❌ |
| `config_describe` | 看某份配置的详情：引擎、模型、prompt、是否公网可读等 | ❌ |
| `config_apply` | **永久**切换激活档案（供用户明确要求时用） | ✅ |
| `transcribe_*` | 单次调用可临时指定，不写盘 | ❌ |

`config_list` 的输出里 **api_key / token 一律掩码**（复用 `llm_providers.mask_secret`）。

### Skill 文件的角色

`SKILL.md` 负责告诉 Agent：

1. 有哪些 `configs/*.json` 可选、各自适合什么场景
2. 各引擎的能力边界（哪些能并发、哪些要公网 URL、哪些依赖 R2）
3. **已知坑**：max_tokens 各家上限不同、抓模型时部分厂商不报上限、
   DashScope 只认 `-filetrans` 异步模型、长任务别并发 LLM
4. 默认配置是哪个

Skill 是**知识层**，MCP 是**能力层**，两者分离：换 Agent 也能复用同一份 Skill。

## 四、并发策略（拍板项 3 的具体规则）

### 4.1 引擎级：ASR 阶段

| 引擎 | 允许并发 | 依据 |
|---|---|---|
| `funasr`（本地） | **1** | GPU 显存独占，模型常驻 |
| `qwen_asr`（本地） | **1** | 同上，且 5 分钟切段本来就吃显存 |
| `whisper`（本地） | **1** | 同机 CPU 线程互抢 |
| `xf_asr`（云端） | 2 | 异步接口，但有 RPM |
| `custom_post` openai_compat | 2 | 上传 + 等待，IO 密集 |
| `custom_post` dashscope_async | 2 | 提交后服务端排队，本地只等轮询 |

**默认一律 1**，用户要调才放开，且每次放开都在日志里明确记「用户手动放开到 N」。

### 4.2 阶段级：**LLM 整理阶段锁 1**（你特别点出的）

理由不是"技术上不能"，而是**代价明显大于收益**：

1. **触发限速** —— 本轮刚踩过：MiniMax 429 `Token Plan 用量上限`。
   并发 N 条长文 = 同时打 N 次配额，很容易从"能用"变成"被限"
2. **单条就很慢** —— 实测 general_article 生成 3.6K 字要 **42 秒**。
   并发不会让它更快，只会让所有请求都变慢到超时
3. **成本不可控** —— 并发下失败重试的成本成倍放大
4. **收益低** —— 整条流水线的耗时大头在 ASR，不在 LLM

例外：用户显式配了多个**不同厂商**的 LLM 档案时，可以按厂商分片并发
（DeepSeek 一个、MiniMax 一个，互不共享配额）。默认不做。

### 4.3 流水线模型

关键：**文件之间可并发，单个文件内部严格串行**。

```
文件A: [ASR] → [LLM]     ┐
文件B: [ASR] → [LLM]     ├─ pipeline_concurrency = 2 时
文件C: [ASR] → [LLM]     ┘
   ▲ 同一时刻最多 2 个 ASR、最多 1 个 LLM
```

实现上用两个独立的信号量：
- `asr_sem`（容量 = 引擎允许并发）
- `llm_sem`（**固定 1**）

这样既利用了云端 ASR 的等待时间，又不会把 LLM 打爆。

## 五、异步台账 + 心跳（拍板项 1）

### 5.1 目录

```
data/mcp_tasks/<task_id>/
├── task.json      # 参数 / 状态 / 进度 / 结果（每完成一项就落盘）
├── job.log        # 完整 stdout
└── cancel.flag    # 存在即取消
```

### 5.2 状态机（**只有 4 态**）

```
queued ──→ running ──┬──→ succeeded
                     └──→ failed        整体失败（配置错 / 引擎不可用）
       │
       └──→ interrupted                 进程死掉但有未完成项（心跳超时判定）
```

`interrupted` 是关键状态 —— 它让"被杀"变成可识别的正常状态，
而不是静默丢失。

### 5.3 心跳协议

- 工作线程每完成**一项**写一次 `task.json`（含 `heartbeat_at`）
- `transcribe_status` 发现 `state=running` 且 `heartbeat_at` 超过阈值（如 10 分钟）
  → 改判 `interrupted`，返回「已完成 N/M，可直接重跑（skip_existing 会跳过已完成的）」
- **HTTP 部署下 server 独立于客户端**，进程被杀的风险大幅降低；
  心跳主要用于兜底 server 自身崩溃 / 机器休眠

### 5.4 为什么 HTTP 更安全（决策 2 的收益）

stdio 下 Agent 关客户端 = server 死 = 任务全丢。
HTTP 下 server 是独立进程，Agent 只是它的客户端，断线重连即可。

**但仍有一个坑**：HTTP server 重启后，内存里的任务引用丢了。
→ 恢复逻辑：启动时扫 `data/mcp_tasks/*/task.json`，
把 `running`/`queued` 的标记为 `interrupted`，让 Agent 决定是否重跑。

## 六、工具清单

| 工具 | 同步/异步 | 写盘 | 说明 |
|---|---|---|---|
| `config_list` | 同步 | ❌ | 列出配置文件 + 档案（脱敏） |
| `config_describe` | 同步 | ❌ | 某份配置的引擎/模型/prompt/可读性 |
| `config_apply` | 同步 | ✅ | 永久切换激活档案（需确认） |
| `engine_capabilities` | 同步 | ❌ | 各引擎能力边界：并发数、要不要公网 URL、模型名清单 |
| `transcribe_plan` | 同步 | ❌ | **只规划**，返回会做什么/跳过什么/多久 |
| `transcribe_batch_start` | **异步** | ✅ | 提交后台任务，返回 task_id |
| `transcribe_status` | 同步 | ❌ | 进度 / 结果 / 补救脚本 |
| `transcribe_cancel` | 同步 | ✅ | 置 cancel.flag |
| `transcribe_from_raw` | 同步 | ✅ | **只重整不重转**（本次排障的痛点） |
| `transcribe_recheck` | 同步 | ✅ | 复查 + 生成补救脚本 |

### `transcribe_plan` 出参（最有价值的一个）

```jsonc
{
  "planned": 8, "skipped": 5, "remaining_after": 12,
  "status_counts": { "complete": 5, "raw_only": 3, "unprocessed": 12 },
  "est_minutes": 18,
  "asr_concurrency": 2, "llm_concurrency": 1,
  "items": [
    { "source": "1.56画面的色彩与夸张变化.mp4",
      "status": "raw_only",
      "raw": "output/local/.../raw.md",
      "articles": ["output/local/.../general_article.md"],
      "reason": "有 raw.md 但缺整理版" }
  ],
  "warnings": ["引擎 custom_post 需要图床公网可读；当前 provider=r2, public_base_url 为空，将走签名直链（有效期 3600s）"]
}
```

`warnings` 是重点：把**跑之前就该知道的风险**提前说，
而不是跑到一半才 403/429（这轮已经吃了两次这种亏）。

## 七、实施顺序

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **P0** | `config_list` / `config_describe` / `engine_capabilities` / `transcribe_plan`<br>**全部只读**，零风险 | 无 |
| **P1** | HTTP server 骨架 + MCP 注册 + Claude Desktop 配置 | 2 |
| **P2** | `transcribe_from_raw`（单文件同步，本次排障痛点） | 4 |
| **P3** | 异步台账 + 心跳 + `start`/`status`/`cancel` | 1、3 |
| **P4** | `transcribe_recheck` 收尾闭环 + 启动时恢复 interrupted | P3 |
| **P5** | SKILL.md（配置清单 + 能力边界 + 已知坑） | P0–P4 |

**从 P0 开始的理由**：零写入、零异步、零并发，能立刻让 Agent 回答"还剩多少、为什么跳过"，
而且它是后面所有阶段的地基（配置解析、能力查询都是共用的）。
