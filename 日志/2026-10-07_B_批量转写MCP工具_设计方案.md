## 一、先说结论：值得做，但不是"为了批量"

现有 CLI 的批量能力**已经很完整**，不是短板：

| 已有能力 | 实现位置 |
|---|---|
| 目录递归扫描 / 清单文件 | `batch.py: find_local_videos` / `read_batch_file` |
| 断点续传（跳过已完成） | `processor.py: plan_batch_urls` 的 `skip_existing` |
| 批量执行 + 自动补救轮次 | `processor.py: process_batch` 的 `auto_repair/repair_rounds/repair_delay` |
| 报告复查 + 生成补救脚本 | `processor.py: check_batch_report` |
| 输出路径单一真源 | `output_manager.py: build_output_paths` |
| 预览/试跑/写清单 | `--dry-run` / `--write-list` / `print_output_preview` |

所以 MCP 的增量价值**不在"能批量"**，而在下面三件事：

1. **长任务异步化** —— 实测 23 分钟视频端到端 2.2 分钟（DashScope 转写 35.9s + 整理 42s）。批量 50 个就是 **1–2 小时**。MCP 单次调用有超时，必须做成"提交 → 轮询"，否则 Agent 只能干等或超时。
2. **结果结构化** —— 现在 CLI 是 `print()` 到 stdout。人看没问题，Agent 拿不到可靠的"哪几个失败了、失败原因分别是什么"。
3. **让 Agent 中途决策** —— 看到「7 个失败：3 个 ASR 超时、2 个 LLM 429、2 个标题为空」，Agent 才能决定"换引擎重试前 3 个 / 跳过 2 个 / 手工补 2 个"。批量脚本只能一路闷头跑完。

> 一句话：**MCP 是把「一次性批处理脚本」变成「Agent 可驱动的流水线」**。

## 二、三个核心设计决策

### 决策 1：复用，不重写（最重要）

MCP 工具**内部直接 import 现有函数**，**绝不 subprocess 调 `transcribe.py`**。

理由：
- subprocess 只能拿到 stdout 文本，要再写一层正则去解析自己项目打印的格式 —— 这层解析会随项目改动一起烂
- 会产生**两份逻辑**：批量规则（skip_existing 判定、补救轮次）改一次要改两处
- 无法拿到结构化的中间状态

具体复用：

```python
from video_to_article.processor import (
    plan_batch_urls,      # 计划：断点续传 + limit + 状态分类
    process_batch,        # 执行：含 auto_repair
    check_batch_report,   # 复查：产出补救脚本
    process_raw_file,     # 只重整不重转
)
from video_to_article.batch import find_local_videos
from video_to_article.output_manager import build_output_paths
from video_to_article.config import load_config
```

`process_batch` 已经会写 JSON 报告（`results` / `partial_issues` / `auto_repair` / `repair_script`），**那份 JSON 直接就是 MCP 工具的返回体** —— 不需要为 MCP 单独造数据结构。

### 决策 2：异步任务模型（技术核心）

批量任务不能同步跑。设计成一个**极简任务台账**：

```
data/mcp_tasks/
  └── <task_id>/
      ├── task.json     # 参数 + 状态 + 进度 + 结果
      └── job.log       # 完整 stdout（排查用）
```

状态机（**4 态，越少越好**）：

```
queued ──→ running ──┬──→ succeeded
                     └──→ failed      （整体失败：配置错、引擎不可用）
```

进度由 `task.json` 里的计数推进（`done / total / 当前正在处理的文件名`）。

工具侧：

| 工具 | 作用 | 同步/异步 |
|---|---|---|
| `transcribe_plan` | 只规划，返回「会处理哪些、跳过哪些、为什么」 | 同步（秒级） |
| `transcribe_batch_start` | 提交后台任务，立刻返回 `task_id` | **异步** |
| `transcribe_status` | 查进度/结果 | 同步 |
| `transcribe_cancel` | 取消（置标志位，工作线程在每项之间检查） | 同步 |
| `transcribe_recheck` | 复用 `check_batch_report`，返回补救脚本 | 同步 |
| `transcribe_from_raw` | 只重整不重转（`--from-raw` 的 MCP 版） | 同步（单文件） |

**关键约束：MCP server 进程不能被 Agent 关掉。** stdio 模式下 Agent 退出 = server 死 = 后台任务全丢。
→ 解法见决策 3。

### 决策 3：部署形态（**需要你拍板，见第五节**）

| | **stdio**（推荐起步） | **HTTP/SSE** |
|---|---|---|
| 启动 | MCP 客户端拉起子进程 | 独立服务，先手动起 |
| 多客户端同时用 | ❌ 一对一 | ✅ |
| 跨会话存活 | ❌ 随客户端退出 | ✅ |
| 长任务安全 | ⚠️ 靠决策 4 兜 | ✅ 天然安全 |
| 配置复杂度 | 低 | 中 |

## 三、工具清单（入参 / 出参）

### 1. `transcribe_plan` —— 先看再跑

```jsonc
// 入参
{
  "sources": ["E:/.../1-课件"],       // 目录 / 单文件 / URL 列表 / 清单文件路径
  "recursive": true,
  "limit": 10,                        // 0 或省略 = 不限
  "prompts": ["general_article"],
  "asr_engine": "custom_post",
  "skip_existing": true,
  "batch_root": null
}
```
```jsonc
// 出参
{
  "planned": 8,
  "skipped": 5,                 // 已完成
  "remaining_after": 12,
  "status_counts": { "complete": 5, "raw_only": 3, "unprocessed": 12 },
  "items": [
    { "source": "1.56画面的色彩与夸张变化.mp4", "status": "raw_only",
      "raw": "output/local/.../raw.md",
      "articles": ["output/local/.../general_article.md"],
      "reason": "有 raw.md 但缺整理版" }
  ],
  "estimated_minutes": 18
}
```

**这是最有价值的一个工具** —— `--dry-run` 已有全部逻辑，只是输出是给人看的 print。
它让 Agent 在花钱之前先回答"到底要干什么、花多久"。

### 2. `transcribe_batch_start` —— 提交

```jsonc
// 入参：同 plan 的参数 + 额外的
{ "concurrency": 1, "auto_repair": true, "cover_pipeline": "off" }
```
```jsonc
// 出参
{ "task_id": "b-20261007-213045-a1b2", "planned": 8, "queued_at": "..." }
```

⚠ **并发默认必须 = 1**。理由：云端 ASR 有速率限制，且每项都要传音频到 R2/DashScope。
并发开大会直接触发限速（RPM），反而更慢且更容易失败。
本地 funasr 则受显存限制，本来也只能串行。

### 3. `transcribe_status`

```jsonc
{
  "state": "running",
  "done": 3, "total": 8, "failed_so_far": 1,
  "current": "1.57xxxx.mp4",
  "eta_minutes": 11,
  "results": [ /* 复用报告里的 results 结构 */ ],
  "partial_issues": [ /* 有 raw 没成稿的 */ ],
  "repair_script": "data/batch/xxx/补漏.ps1",
  "log_tail": "……最后 30 行……"
}
```

### 4. `transcribe_recheck` —— 收尾自查

跑完一遍后复查"哪些该有而没有"，并返回现成的补救脚本。这是**收尾的关键动作**，
现在的 `--check-report` 只打印，暴露成工具后 Agent 会主动在最后调它。

### 5. `transcribe_from_raw` —— 补整理版

这次排障里最有用的一个动作（你 10-05 那次就是手动让我做的）。
把 `handle_from_raw` 暴露成工具后，Agent 可以**自己**补齐，不必再找你。

## 四、长任务不丢的兜底（stdio 模式必看）

stdio 模式下 Agent 关掉客户端 = server 进程死 = 后台任务全丢。三层兜底：

1. **心跳 + 断点续跑**：`task.json` 每完成一项就落盘。进程被杀掉后，
   `transcribe_status` 发现 `state=running` 但无心跳 → 标记 `interrupted`，
   Agent 可直接 `start` 重跑 —— `--skip-existing` 会跳过已完成的，**不浪费**。
2. **优先复用 CLI**：如果 Agent 场景下 stdio 不可靠，长任务建议仍走
   `transcribe.py --local-dir ...`（它自带报告 + 补救脚本），MCP 只负责
   `plan` / `status` / `recheck` / `from_raw` 这几个短操作。
3. **HTTP 模式**：进程独立于客户端，天然不丢。

**我的建议：先按方案 2（长任务走 CLI）落地，把 MCP 的价值放在短操作和结构化报告上。**
理由：长任务的异步化是整个方案里最容易出竞态的部分，而它的收益对"批量跑课件"
这个场景并没有 `skip-existing + 报告 + 补救脚本` 实。

## 五、需要你拍板的 5 件事

1. **部署形态**：stdio 起步，还是直接 HTTP？（影响能不能多客户端/跨会话）
2. **长任务走哪条路**：MCP 后台跑（需做异步台账+心跳），还是长任务仍走 CLI、MCP 只管短操作？
3. **并发**：`concurrency` 要不要开放？我倾向先锁死 1，观察限速情况再放开。
4. **写入范围**：MCP 工具允许写 `output/` 和 `data/`，还是只允许读 + 返回"该跑什么命令"让你自己敲？
   （涉及是否要确认写入动作）
5. **暴露给谁**：只给 MCode 用（一个客户端），还是想同时挂到 Claude Desktop？

## 六、分阶段实施（每阶段都能独立用）

| 阶段 | 内容 | 产出 | 依赖拍板 |
|---|---|---|---|
| **P0** | 只读工具：`transcribe_plan` / `transcribe_status` | Agent 能问"还剩多少、为什么跳过" | 无（纯只读，零风险） |
| **P1** | 写操作：`transcribe_from_raw` | Agent 能自己补整理版（这次排障的痛点） | 4 |
| **P2** | `transcribe_recheck` + 收尾闭环 | 跑完自动自查并给补救脚本 | 4 |
| **P3** | 异步批量（若 2 选了 MCP 后台） | 真正的"提交-轮询" | 1、2、3 |

**建议从 P0 开始** —— 它零风险、不需要拍板任何有争议的点，
但已经能让 Agent 在你问"还剩几个"时直接回答，而不是让你自己去翻目录。
